# Production Readiness

spex is production-candidate software. Treat production use as gated until these checks are true for the target scenario repository and platform environment.

## Required Gates

- CI runs `spex suite validate`, `suite plan --format json`, `suite explain --format json`, `catalog check --format json`, `catalog docs`, and `suite compile`.
- Project CI runs `make verify`, which covers Go module verification, Go tests, integration script smoke checks, and verified release archive validation.
- Project CI runs `make security-check` with the scanner installed by `make install-vulncheck` or an equivalent pinned vulnerability scanner gate.
- Project CI runs `make reference-scenario-check` to prove the separate scenario repository workflow remains usable.
- Release-candidate CI runs `make production-candidate-check` before a live proof is attempted.
- CI runs `spex doctor --skip-host-tools --require-pinned-git-refs` so external `bindingRef`, `integrationProfileRef`, and `catalogRefs` do not use mutable refs such as `@main` or `@master`.
- Production scenario repositories using registry-hosted probe images run `spex doctor --require-pinned-images` so probe image references are pinned by a valid `@sha256:<64 hex chars>` digest.
- CI runs `spex doctor --scan-artifacts reports --scan-artifacts generated` after compile/run with `SPEX_*` secret environment variables present.
- Live CI jobs delete generated kubeconfig files before artifact upload and run `spex doctor --scan-artifacts` against live output with the same representative secret values used during the run.
- Scenario repos generated by `spex init scenario-repo` can run the non-cluster production gate with `SPEX_PRODUCTION_CHECK=true ./ci/spex-validate.sh`.
- Release artifacts are built with injected `VERSION`, `COMMIT`, and `BUILD_DATE`; `go-modules.txt`, `dependency-inventory.json`, `buildinfo.txt`, `third-party-licenses.txt`, `release-provenance.json`, `SHA256SUMS`, `version.json`, and `release-manifest.yaml` are archived.
- Release directories pass `spex release verify --dist <dist-dir>` before publication. Published tarballs pass `spex release verify --dist <dist-dir> --archive <archive>`. Archive creation is non-overwriting by default; use `--force` only in disposable verification directories.
- Live proof runs are repeated on a clean kind cluster before promoting changes that alter bindings, integration profiles, probe images, or catalogs.
- Scenario repositories pin catalog and binding refs to immutable tags or commit SHAs.
- Generated workspaces and reports are retained as CI artifacts for failed runs.
- GitHub Actions checkout disables persisted credentials unless a job explicitly needs to push.

## Security Notes

`--scan-artifacts` searches generated files for exact secret values from selected environment variables and fails if kubeconfig files are present. It reports only the environment variable name and file path. It does not replace a formal security review and cannot detect secrets that are not present in the process environment.

Generated manifests should contain Secret names, key names, SSM parameter paths, and environment variable references. They must not contain raw passwords, bearer tokens, API keys, or Keycloak client secrets.

Live proof output can include host-local paths, temporary kubeconfig references, and cluster diagnostics. Promotion workflows must scrub generated kubeconfigs before artifact upload. Upload live artifacts only after the secret-value scan has completed.

## Compatibility Notes

The current schema family is `v0.1`:

- `spex.scenario.v0.1`
- `spex.suite.v0.1`
- `spex.binding.v0.1`
- `spex.integration.v0.1`
- `spex.catalog.v0.1`

Until a `v1` schema is introduced, treat schema changes as release-candidate compatible only after running the generated scenario repo checks and live proof. Do not rely on undocumented fields.

## Promotion Checklist

1. Project repo `make verify` passes.
2. Project repo `make install-vulncheck && make security-check` passes.
3. `make production-check` passes for release-candidate artifacts.
4. Scenario repo `make ci` passes.
5. Scenario repo `make production-check` passes.
6. At least one clean kind live run passes for the target profile.
7. A failed-run artifact bundle has been inspected for useful remediation data.
8. Secret leakage scan passes with realistic secret environment variables.
9. Remote refs are pinned to immutable tags or commit SHAs.
10. Registry-hosted probe images are pinned by digest.
